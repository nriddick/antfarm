WIN-005 [P2] MT Fiber benchmark overstates drain throughput (not Windows-only)

fibers/benchmarks/benchmark_mt.d times burstSpawn and waitDrained separately,
but workers execute during burstSpawn. The printed run rate divides the full
100,000-Fiber count by only the residual drain duration. One Windows capture
spent 1.073120 s spawning and 0.000028 s draining, yet printed billions of
fibers/s. This is not a valid measure of completed-burst throughput.

Reporting mitigation implemented and tested: parse_fiber uses the sum of the
creation and drain durations for MT primary throughput, validates matching
positive counts, and invalidates legacy cached MT metrics. Saved raw output
is unchanged; derived summary metrics were recalculated from those captures.
Cold median: 96,960 fibers/s [87,484, 250,305]; warm median: 1,372,401
[783,773, 1,419,729]. Retained Ryzen drain readouts are explicitly marked
legacy/not comparable, rather than silently treated as full-burst throughput.
Follow-up: fix raw benchmark labels/timing, and characterize full-burst MT
throughput on Linux before making cross-host scheduler comparisons.

CONFIRMED RUNTIME BUG

WIN-001 [P1] Windows pool disregards process affinity and runs outside it

Trigger: start a default CacheAwarePool in a process limited to CPU mask 0x3
(LPs 0 and 1), or 0x3000 (LPs 12 and 13).
Expected: select only allowed processors, create two workers, and execute
callbacks exclusively on those processors.
Actual, in all four compiler/mask combinations:
  process mask=3 or 3000: physical snapshot=20, eligible=2,
  workers=20, observed CPUs=fffff
The probe first confirms excluded processors have parkedAtDiscovery=true.
The observed mask is recorded by callbacks using GetCurrentProcessorNumberEx;
0xfffff proves callback execution on LPs 0 through 19, outside either mask.
This is more than a reporting/count issue: worker pinning overrides the
requested CPU restriction. Resource partitioning and isolated timing can fail.

Relevant code:
  threadpool/source/threadpool/pool.d:641, selectLps
  threadpool/source/threadpool/pool.d:671, unavailable-processor filtering
    is inside version(linux), so Windows ignores the discovery flags.
  threadpool/source/threadpool/pool.d:728, existing unit test explicitly
    expects both processors on non-Linux even when one is marked parked.
  threadpool/source/threadpool/pin.d:32, SetThreadGroupAffinity pins those
    excluded processors successfully on this Windows host.

Reproduce from the repository root in PowerShell:
  $verifyPython = 'C:\Users\natha\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe'
  & $verifyPython .build/windows-verification/run.py affinity

Probe source: .build/windows-verification/affinity_probe.d
Evidence: affinity-probe-{dmd,ldc2}-mask-{3,12288}.log in the same directory.
The four run commands intentionally fail the final two-worker assertion.
Fix direction: represent process eligibility separately from transient OS
parking, enforce eligibility in Windows worker selection and pinning, and
add tests for both masks and explicit processor selections. Simply skipping
every Windows parked CPU would also change normal parked-core behavior.

WINDOWS BUILD AND VALIDATION GAPS

WIN-002 [P2] Default Windows Debug mimalloc archive cannot link into D suite

The pinned static allocator builds with MSVC in both Release and Debug.
Release links and passes the real allocator actor suite with both compilers.
The corresponding Debug archive fails to link with both compilers:
  error LNK2001: unresolved external symbol __imp__CrtDbgReport
  fatal error LNK1120: 1 unresolved externals
This establishes a Windows debug CRT pairing/build gap, not an allocator
runtime corruption. There is currently no dedicated Windows Debug recipe;
the documented Dub configuration selects Release and passes.

Reproduce:
  & $verifyPython .build/windows-verification/run.py allocator
This configures the vendored allocator with MI_OVERRIDE=OFF,
MI_BUILD_SHARED=OFF, MI_BUILD_STATIC=ON, MI_BUILD_OBJECT=OFF,
MI_BUILD_TESTS=OFF and MI_OPT_ARCH=OFF, builds Release and Debug, then links
actor_torture with AntfarmActorTestHooks, AntfarmMimallocV3 and
AntfarmMimallocReal. Exact commands are saved in allocator-results.json.
Evidence: actor-real-mimalloc-Debug-{dmd,ldc2}-build.log.
Follow-up: define/document compatible MSVC CRT flags for a Windows full-debug
allocator lane, retaining allocator checks and cross-thread-free validation.
