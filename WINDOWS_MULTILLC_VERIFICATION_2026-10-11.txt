WML-01 [P1] DMD idle worker busy-loops instead of parking
-------------------------------------------------------
Reproduce from threadpool:
  dub test --compiler=dmd

All three attempts failed at source/threadpool/pool.d:813, "worker never
parked", in the new wakeLlc unittest (starts at line 793). After reporting
1/8 modules FAILED, the process did not exit. The first attempt was terminated
at 240 seconds; two repeats were terminated at 45 seconds each.

An independent, non-unittest executable also reproduces the idle problem:
one CacheAwarePool worker on ProcessorId(0, 0), default wait policy, and a
callback that atomically increments a counter and returns false. After ten
20-ms observations DMD had about 5.9 million callback invocations and 2.9
million park attempts. The policy remained IdleKind.wait (3), and startup
reported pinned. An unmatched wakeLlc was unnecessary for the counter to
continue increasing. Explicit shutdown completed in this isolated probe.

The equivalent LDC executable parked at two callbacks. A wake for another LLC
left the count at two; a matching wake raised it to four. Three pool lifecycles
passed. LDC's complete threadpool unit suite also passed.

Impact: idle DMD workers can consume a CPU; the unit failure also hangs a test
invocation unless it has an external timeout. This is not merely a too-short
unit-test deadline. Root cause and introduction point are not yet established.
Investigate hybrid.d:285 applyIdlePolicy and sys/win_wait.d:102 parkWorker,
including DMD argument passing and the wait API outcome. Keep the cleanup/hang
symptom separate until its cause is established.

Evidence: threadpool-dmd-unit.log, threadpool-dmd-repeat-1.log,
threadpool-dmd-repeat-2.log, wake_probe.d, wake-probe-dmd-run.log,
wake-probe-dmd-counters.log, wake-probe-ldc2-run.log.

WML-03 [P2] Performance report rejects valid MT Fiber output
-----------------------------------------------------------
fibers/benchmarks/benchmark_mt.d:37 report() now prints "not measurable
(finished before the timer started)" instead of a numeric drain interval when
the workers drain a burst during spawning. This is a legitimate benchmark
outcome, not a failed runtime operation.

Observed with:
  cd fibers
  dub run -c benchmark_mt --compiler=ldc2 --build=release -- 1000 assist

The saved output includes:
  run    (warm pool): 1000 fibers: not measurable (finished before the timer started)

Feeding that exact successful output to parse_fiber in
perftest/run_performance_md.py raises:
  ValueError: no complete multithread fiber burst timings

The parser requires numeric create/run intervals for both cold and warm bursts
(lines 186-200); it also requires a numeric cold drain rate (lines 184-185).
Thus either burst can break the report depending on scheduling and workload.
Existing Python parser tests passed but do not cover this real output.

Suggested follow-up: emit an explicit numeric end-to-end burst duration even
when the residual drain rate is not meaningful, and teach the report parser
that format. Do not invent a zero drain time from a message that omits timing.

Evidence: fibers-ldc2-mt-assist.log and fiber-parser-repro.log.

WML-04 [P3] Windows offccd sweep omits executable hashes
-------------------------------------------------------
Reproduce from the root after perftest/build-windows.ps1:
  python -B perftest/offccd_sweep.py --suite smoke --out NEW_DIRECTORY --runs 1 --topup-runs 0 --window-ms 100 --timeout 30 --bin-dir perftest

The sweep successfully runs offccd.exe and c2c.exe, but metadata.json contains
"binaries": {}. host_metadata at perftest/offccd_sweep.py:297 checks extensionless
paths with Path.exists(), which does not find these Windows .exe files.
Windows process launch accepts the extensionless commands, so execution
success masks the metadata omission.

Impact: saved Windows runs cannot identify the actual measured executables by
hash. Resolve the executable path once, including .exe on Windows, and reuse
it for execution and metadata; add a Windows-style file fixture.
Evidence: offccd-sweep-smoke.log and offccd-smoke/metadata.json.

Synthetic Windows processor-group coverage added
------------------------------------------------
threadpool/tests/topology_parse.d now includes two focused fixtures:
- 128 logical processors in two complete 64-LP groups, with separate LLCs and
  packages, SMT pairs, LP 63 high mask bits, repeated group-relative LP/core
  numbers, and relation-group records. Checks parsing, group-qualified lookup,
  full and SMT-filtered pool resolution, sparse affinity eligibility, duplicate
  requests, excluded/unknown CPUs, accepted group count, and CPU-list roundtrip.
- One L3 relationship spanning two processor groups, including bit 63 in group
  zero and bit zero in group one; checks unified LLC membership and cache size.

Both pure fixtures passed when compiled and run independently with DMD and
LDC. They also passed as part of the full LDC threadpool unit suite. The DMD
full suite remains failed because of WML-01. No synthetic test invokes a real
pin operation or starts a worker on a nonexistent CPU.

Recommendation: YES to these plumbing tests. Keep real multi-group execution
and real cross-LLC scheduler behavior explicitly unvalidated. Windows processor
groups are bounded by logical processors, not physical core count; >64 logical
processors is the relevant boundary. Microsoft documents different default
cross-group affinity behavior beginning with Windows 11 / Server 2022:
https://learn.microsoft.com/en-us/windows/win32/procthread/processor-groups
