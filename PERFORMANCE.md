# Ant Farm performance

Measured performance for the current development line. Every number below was
taken now, at commit `69ef010`, on one host; the raw process output is
regenerated by `perftest/run_performance_md.py` and is deliberately not
committed. Historical measurements were archived outside the repository and are
not reproduced here.

- Harness and mode index: [perftest/README.md](perftest/README.md).
- Committed-ref optimization gate: `make perf-gate`; rules in
  [perftest/README.md](perftest/README.md#optimization-gate).
- Fiber-specific profiling and tuning: [fibers/PERFORMANCE.md](fibers/PERFORMANCE.md).
- Stable sizing formulas: [ARCHITECTURE.md](ARCHITECTURE.md#sizing-one-farm) and
  [SPEC.md](SPEC.md).

## Scope and caveats

These are synthetic microbenchmarks on one machine. They isolate transport and
lifecycle overhead; they are not predictions for application work.

- **Host.** AMD Ryzen 5 5500, 6 physical cores / 12 logical processors, one
  16 MiB L3. Linux 7.2.8 (CachyOS), x86-64.
- **Compilers.** LDC 1.43.0 (`ldc2 -O2 -release`), DMD 2.113.0 for the
  documented fallback builds. The Fiber numbers use a DUB `release` LDC build.
- **Allocator.** Actor numbers use the pinned mimalloc 3.5.3 archive
  (`actor_torture/.build/mimalloc-v3.5.3/libmimalloc.a`, sha256
  `551ee9a9…a1bec`) unless the table says `crt`. Payload numbers use the process
  C runtime.
- **Huge pages.** `ANTFARM_HUGE_PAGES=0` (ordinary 4 KiB pages) except in the
  huge-page comparison. The sandbox exposes no THP or cpufreq sysfs files, so
  the kernel governor and THP mode were not readable; the huge-page rows set the
  Farm request explicitly.
- **Host load.** Per-run load was captured only for the rerun cells. Single
  producer 0.99–4.75, private emitter count 1.55–2.39, single-thread Fiber runs
  0.17–0.35, tail run 1 0.32 with the rest 7.4–8.0 (likely the tail harness's
  own spinning threads), and `benchmark_mt` 6.4–8.0 inherited. The remaining
  cells have no per-run load record, so treat them with the shared-host caveat.
- **Tail topology.** `tail` and the Fiber `benchmark_mt` read
  `threadpool.topology` (`CacheAwarePool.topology()`), which needs
  `/sys/devices/system/cpu`. Only when `/sys/devices` is entirely absent, pass
  `--fake-topology`: the script synthesizes a tree from `/proc/cpuinfo` (cache
  sizes hard-coded for this Ryzen 5 5500; adjust for other hosts) at the
  hardcoded path, removes exactly what it created, and refuses on a real sysfs
  mount. It needs a writable non-sysfs `/sys`.

### What the units mean

| Unit | Benchmark | Meaning |
| --- | --- | --- |
| **Mpps** | `throughput`, `dual` | million payload `Call`s per second; one item is one published payload |
| **Mactor_cycles/s** | `actor_churn` | million complete actor lifecycles (create → dispatch → retire → reclaim) per second |
| **Mselected_callbacks/s** | `actor_churn subset*` | million selected subset callbacks per second |
| **Mactor/s** | `actor_ready` | million actor activations per second from a prequeued burst |
| **fibers/s** | `fibers` DUB benchmarks | Fiber creations (cold/warm) or scheduler resumptions per second |
| **ns** | `tail` | sentinel write-to-first-`Call` latency |

Tree modes count leaf lifecycles, so `tree` and `tree-slab` are directly
comparable to each other and to `private`; a fanned-out cohort adds no units.

## Method

Build the harness once, then run the matrix into a scratch directory:

```sh
make -C perftest all
make -C perftest actor_churn_mimalloc       # real mimalloc archive must exist
python3 perftest/run_performance_md.py      # writes /tmp/antfarm-perf-report
python3 perftest/run_performance_md.py --sections tail,fibers --fake-topology
```

The script writes `metadata.json`, one raw capture per run under `raw/<section>/`,
and `summary.json` with median/min/max per cell. It runs 5 times per cell with
`ANTFARM_HUGE_PAGES=0` unless a cell opts in. A run counts only when the process
exits 0 and its metric parses; a cell with fewer than 5 valid runs is failed and
the script exits nonzero. Re-running resumes a cell only when its stored argv
and env match. Raw output is archived, not committed.

Every table reproduces from the script's cells; the exact argv is each cell's
`cmd` in `summary.json`. Payload tables use the 16 MiB ring (`--ln 2097152
--k 8`); actor tables use the harness's 8 MiB ring, with the controller plus one
pinned worker per listed consumer.

Compare a change against a committed ref with:

```sh
make perf-gate BASE=<sha> CANDIDATE=<sha>
make perf-gate BASE=<sha> PERF_GATE_ARGS=--control
```

Gate rules (full text in [perftest/README.md](perftest/README.md#optimization-gate)):

- Exit 0 pass, 1 regression, 2 inconclusive/error; inconclusive is never a pass.
  The regression boundary is **−3%** on the paired-median decision.
- Near the boundary, rerun with `PERF_GATE_ARGS=--boundary` for **≥20 process
  pairs** plus a byte-identical control (`PERF_GATE_ARGS=--control`, base built
  twice; hashes must match). Individual pairs may dip below −3% while the cell
  passes if the paired-median interval's lower bound is above −3%; harness bias
  is about ±1.5%.
- At 0 consumers code layout alone can move single-threaded cells; attribute a
  near-boundary swing with an inert-code control. That waiver is one-off.
- Run correctness first, then timing serially on a quiet host.

### Best configuration: the >1B items/s headline

The best measured configuration exceeds 1B items/s at a batch near 1700 and a
128-entry claim. It needs several small producers, 8 consumers, a one-word body,
the arithmetic write form, and chunk 128:

```sh
./perftest/throughput --once --constant-callandlength \
  --n 2000000000 --body 1 --batch 1700 --ac 0 --nb 0 --ns 4 --nc 8 --repeats 1
```

The default-chunk and single-producer rows use the same writer and geometry with
`--ac 3` and `--ns 1 --nc 11` respectively, and the same `--nb 0 --repeats 1`.

| Configuration | Mpps | items/s |
| --- | ---: | ---: |
| 4 small producers, 8 consumers, body 1, batch 1700, chunk 128 | **1,244 [1,218, 1,276]** | **1.24B** |
| same, default chunk 16 (`ac 3`) | 1,169 [1,137, 1,210] | 1.17B |
| 1 small producer, 11 consumers, body 1, batch 1700, chunk 128 | 342.5 [341.4, 345.3] | 0.34B |
| default shape (1 bulk producer, 4 consumers, body 16, batch 80) | 78.4 [78.2, 78.6] | 0.08B |

Both the headline and the default-chunk row exceed 1B items/s, so the >1B rate
comes from the configuration, not from the claim size alone. A single producer
reaches only about a quarter of that (342 vs 1,244 Mpps, with 11 consumers), so
the aggregate rate comes from several producers filling the ring. Chunk 128 is
worth about 6% over the default at this shape.

### Single-threaded table layouts vs MT tables

A table of only single-threaded payloads (`Tmt == 0`, every payload
`MaxCs == 1 && Done == 1`) stores each payload as a compact `[Call][Pbody]`
record (SPEC 2f), or, when the accepted prefix shares one `Call`, as the bare
`[Pbody]` with the `Call` stored once per table (SPEC 2g). A uniform table whose
bodies also share one nonzero length drops Tindex as well. A table containing a
multi-threaded payload keeps the full `Phead` layout. Geometry, ignoring table
overhead:

| Format | Ring words per entry | Entries per 4096-word small quota |
| --- | --- | ---: |
| Uniform `Call` and length, 1-word body | 1 (body) | ≈4096 |
| Uniform `Call` and length, 16-word body | 16 | ≈256 |
| Uniform `Call`, 1-word body | 2 (1 index + 1 body) | ≈2048 |
| Uniform `Call`, 16-word body | 17 | ≈241 |
| Compact ST, 1-word body | 3 (1 index + 1 `Call` + 1 body) | ≈1360 |
| Compact ST, 16-word body | 18 | ≈227 |
| MT full, 1-word body | 18 (1 index + 16 `Phead` + 1 body) | ≈227 |
| MT full, 16-word body | 33 | ≈124 |

Compact tables admit several times more entries per quota than the full layout,
which is why the per-object allocator geometry shifts in the private-remote
churn cell (see [Allocators](#allocators)); uniform tables admit up to three
times more again.

Today's benchmarks all build ST tables (the payload harnesses and actor layers
set `MaxCs = Done = 1`). Unless a section says otherwise, its numbers were
measured on the compact layout, before uniform tables (SPEC 2g) landed; the
harnesses now publish uniform tables wherever a table's callbacks are shared
(`throughput --mixed-calls` keeps the compact layout). The MT path is exercised only by the correctness suite
(`antfarm_test`, `review_torture`), and this is not a pre-compact comparison.

### Cohort slab vs per-object

The slab reserves every member's state at cohort creation, so retirement is one
free per cohort instead of one per member. Same shapes as above at 6 consumers:

| Workload | Per-object | Cohort slab | Change |
| --- | ---: | ---: | ---: |
| `tree` | 57.32 | 207.29 | +262% |
| `tree-wait` | 57.13 | 193.60 | +239% |
| `tree-refill` | 70.91 | 273.16 | +285% |

At 0 consumers the slab is also ahead (`tree` 81.25 → 105.27; `tree-wait`
81.59 → 106.16; `tree-refill` 94.14 → 127.53), but the 6-consumer case is where
the per-member cross-thread free dominates. The slab's cost is the full
`capacity * T.sizeof` reservation for the cohort's life plus one larger free; it
is the right choice for a cohort whose members all live and die together.

### Batch limit and work-cost hints

Root tables derive their claim class from the table width and live consumer
count (`rootCostHintFor`), capped at 32-entry claims. Passing an explicit class
overrides it. `tree` and `private` at 6 consumers:

> **Stale.** This table predates uniform tables (SPEC 2g) and the sharded split
> rule below. `tree` batch 256 auto now derives class 3 (64 entries, six claims
> over three shards); the batch 1024 and `private` rows derive the same class
> as before.

| Shape | `root-hint` | Derived class | Table width | Claims | Mactor_cycles/s |
| --- | --- | ---: | ---: | ---: | ---: |
| `tree` batch 256 | auto | 2 | 64 | 2 | 56.91 [56.67, 57.13] |
| `tree` batch 256 | 2 | 2 | 64 | 2 | 56.84 [56.52, 57.17] |
| `tree` batch 256 | 0 | 0 | 64 | 1 | 56.63 [56.37, 56.96] |
| `tree` batch 1024 | auto | 6 | 16 | 8 | **88.47 [85.67, 89.59]** |
| `tree` batch 1024 | 2 | 2 | 16 | 1 | 18.26 [18.15, 18.44] |
| `tree` batch 1024 | 0 | 0 | 16 | 1 | 18.12 [17.91, 18.38] |
| `private` batch 256 | auto | 2 | 256 | 8 | 30.81 [30.57, 30.92] |
| `private` batch 1024 | auto | 2 | 1024 | 32 | 29.71 [29.61, 29.84] |
| `private` batch 1024 | 0 | 0 | 1024 | 8 | 29.44 [29.18, 29.47] |

The important case is the wide root table: a `tree` parent table at batch 1024
holds 16 roots, and the derived hint splits it into 8 two-entry claims across
the consumers (88.5 vs 18.3, about 4.8×). A fixed class 2 (32-entry claims) or a
fixed class 0 (128-entry claims) makes the same 16-entry table a single claim on
one worker. Above the 64-entry small-table threshold the derived hint counts
claims per shard: a sharded table keeps 32-entry claims once they reach the
target, and a table just above the threshold uses shorter claims instead of one
claim per shard. On the uniform layout, 5 paired rounds, that took `tree` and
`tree-wait` at 6 consumers from 59.6 to 74.4 (ratio 1.25 [1.22, 1.26]) and
`tree-refill` from 72.7 to 76.9 (1.06). At 11 consumers `tree` went from 57.0 to
83.2 (1.47), and at 2 consumers every measured mode stayed within ±1%. Its cost
is `tree-slab` at 6 consumers, 0.98 [0.97, 0.98], because the slab parent is
cheap enough that the extra claims cost more than they spread.

Batch size for `private` is flat between 256 and 2048 (30.8 / 29.7 / 31.3); use
the smallest batch that keeps the park's reservation affordable.

| Reclamation | Mactor_cycles/s | cross-thread frees | cross-thread bytes |
| --- | ---: | ---: | ---: |
| emitter-side (`private`) | 30.77 [30.64, 30.91] | 0 | 0 |

The `mimalloc-count` diagnostic counts frees issued by a different thread than
the allocation, across the whole process including warmups. Emitter-side
reclamation frees on the allocating (controller) thread and pays nothing extra;
consumer-side reclamation frees every root remotely and roughly halves
throughput. Choose emitter-side reclamation unless the controller must not
touch consumer-owned state; choose the slab when a whole cohort retires
together. Do not mix slab and per-object policies within one hierarchy.

## Tuning guide

- **Batch size vs `avgCost`.** Batch size is the dominant knob; larger batches
  amortize table overhead up to about 1024, after which the curve flattens. The
  16-entry default claim is a latency-conserving choice; classes 0–2 (128/64/32)
  buy a few percent for uniform cheap callbacks and are the opt-in for
  throughput-bound publishing. Do not pay a longer claim for work that parks.
- **Explicit work-cost hints.** Prefer `rootCostHintAuto` for private root
  tables. A fixed class is only for deliberately serializing or sharding: the
  batch-1024 tree case is about 4.8× slower with a fixed 32- or 128-entry claim
  than with the derived 2-entry claim. A cheap-parent table just above the
  small-table threshold (a slab `tree` at batch 256) is about 2% faster with
  `pump(token, limit, 2)` than with the derived split.
- **Huge pages.** On the headline configuration plus `--huge`
  (`ANTFARM_HUGE_PAGES=1`), huge pages are a modest win (1,302 vs 1,244 Mpps,
  +4.7%, with a wide spread) and neutral for actor work (`actor` 16.66 vs 16.61;
  `tree` 57.07 vs 57.32). Treat them as a payload opt-in; the Fiber package
  document documents a first-concurrent-drain penalty.
- **Quota tiers.** A 4096-word small quota admits about 1360 compact 1-word-body
  entries but only about 227 at 16-word bodies; larger batches are split into
  accepted prefixes, so size `quotaSmall`/`quotaBulk` for the batch you publish.
- **Allocator choice; slab.** mimalloc is decisively faster than the C runtime
  for per-object actor state, and the cohort slab is faster still when a cohort
  retires together. Emitter-side reclamation is the default and avoids remote
  frees; consumer-side reclamation costs roughly half throughput at 6 consumers.
- **Pinning and SMT.** The pinned `actor` curve peaks at 4 consumers (22.69
  Mactor_cycles/s), drops to 16.62 at 6, and an unpinned 6-consumer cell reaches
  21.41. The harness pins the controller to CPU 0 and consumer *i* to CPU *i*,
  so the 6-consumer cell puts consumer 6 on CPU 6, the controller's SMT sibling
  — the same physical core. That fits the 4 → 6 drop and the pinned-vs-unpinned
  gap, and means the flat 6 → 11 comparison already starts with one sibling.
  `tree` is unaffected (56.8 vs 56.9).
- **Known pathologies.** Tiny root tables concentrate all claims on shard 0, so
  a 1% subset at 6 consumers is much slower than the 10% or whole cases. Wide
  root tables with a fixed coarse claim collapse onto one worker (batch-1024
  `tree`). Attribute 0-consumer layout swings with an inert-code control.

### Phase-4 candidates (measured opportunity, not default)

Nothing here is changed in this phase; each would need its own gate.

- **`rootCostHintFor`** already fixes the wide-table case: `tree` batch 1024
  derives class 6 (2-entry claims, 8 claims) and runs 88.5 vs 18.3
  Mactor_cycles/s for a fixed class 2 (32-entry claims), ≈4.8×. `private`
  batch 1024 is within 4% of batch 256, so further gains would be in the
  per-parent callback, not the claim.
- **Child/subset wave chunks** publish a fixed 32-entry claim. The subset 1%/6
  cell (63.1 vs 151.1 at 0 consumers) shows tiny tables centralize; a larger
  claim cannot fix a sub-threshold table, which shard 0 claims wholesale. This
  needs an admission-geometry prototype, not a class bump.
- **Public flush/wave publish chunks** use an 8-entry claim. `wave` at 6
  consumers (17.5) is about two-thirds of its 0-consumer rate (26.4), so wider
  claims may recover some of that; `actor_ready` reaches 60.9 Mactor/s on the
  same flush path. Prototype and gate before changing the internal class.
