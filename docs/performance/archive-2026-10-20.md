## Public actor Part 5 follow-up (1.9.0-progress)

October 20, 2026, i7-12700H, WSL2 Linux, LDC 1.42, mimalloc 3.5.3,
ordinary pages. Runtime candidate: `2eea369`; immediate baseline: `d101485`.
The historical inbox reference is `1495d5b`. All comparisons use identical
`actor_churn` source, 16,384 actors, three-second samples, batch limit 256,
controller CPU 0 and consumers on 2,4,6,8,10,12.

Idle external retirement now release-stores the terminal word after joining
accepted senders and rechecking the idle lifecycle. Its operation pin and
retirement flag exclude remaining writers; debug builds retain an exact-word
CAS that fatals on a violated invariant. The store releases the pin as the
call's final slot access. The
[sole-writer proof](../../docs/design/public-actor-ordering.md#retirement-and-reclamation)
states the acquire/release and reuse obligations.

The generated release code uses an ordinary store and skips the separate unpin.
An uncontended scalar create followed by idle retire/reclaim has **five locked
operations**, down from six: one for creation and four for retirement/reclaim.
These are path counts, excluding allocator internals, retries and dispatch,
not hardware-counter samples.

Batch reservation walks at most **64 free-slot links per gate hold**, then
joins its privately owned chunks outside the gate. All admission still precedes
allocation and initialization. This bounds work per hold, not elapsed latency
or fairness. The deterministic 4,097-slot test pauses between chunks and
requires a remote reclaimer to finish, then verifies occupancy and rollback.
The contiguous free-index-stack proposal remains a separate measured redesign.
The review's gate-hold latency estimates were not reproduced here.

### Changes and atomic-operation budget

Retirement combines its mark and exclusive operation pin in one CAS. Idle
retirement combines its terminal publication and pin release in one exact-word
CAS; running/scheduled retirement retains a separate final unpin. Reclaim still
claims the exact retired generation before touching state. Copied owners retain
their safety guarantees.

Construction and reclamation now update one occupancy counter while holding the
existing free-slot gate. `live` includes the entire reserved construction prefix
as well as unreclaimed actors. It is not a lifetime fence. Shutdown checks zero
occupancy followed by a released free-slot gate, and still requires external
quiescence. Concurrent kind registration uses an append-only atomic list and
adds no work to creation. The [ordering proof](../../docs/design/public-actor-ordering.md#retirement-and-reclamation)
states the final-access and release/acquire arguments.

Uncontended scalar copy/create followed by idle retire/reclaim, excluding
allocator internals, retries, and any dispatch:

| Path | Before | After |
| --- | ---: | ---: |
| Creation locked RMWs | 4 | 1 |
| Idle retirement plus reclaim locked RMWs | 8 | 5 |
| Complete lifecycle | 12 | 6 |

These are path counts from code and generated x86-64 inspection, not hardware
counter samples. The generated `constructReserved` loses both locked counter
updates. The remaining claim CAS is deliberate; no unique-owner shortcut was
introduced.

## Scope and caveats

These are synthetic microbenchmarks on two machines. They isolate transport and
lifecycle overhead; they are not predictions for application work.

- **Hosts.** Ryzen 5500: 6 physical cores / 12 logical processors, one
  16 MiB L3, Linux 7.2.8 (CachyOS). Intel 12700H: 6 performance cores with SMT
  plus 8 efficiency cores / 20 logical processors, Windows 11 build 26200,
  64 GiB RAM. Both are x86-64.
- **Compilers.** LDC `-O2 -release`: 1.43.0 on Ryzen, 1.42.0 on Intel.
  The Fiber numbers use a DUB `release` LDC build on each host.
- **Allocator.** Actor numbers use the pinned mimalloc 3.5.3 archive
  unless the table says `crt`. Windows uses the Release static library with
  the static release CRT; Linux uses `libmimalloc.a`. Payload numbers use the
  process C runtime.
- **Huge pages.** `ANTFARM_HUGE_PAGES=0` (ordinary 4 KiB pages) except in the
  huge-page comparison. The sandbox exposes no THP or cpufreq sysfs files, so
  the Linux kernel governor and THP mode were not readable; the huge-page rows
  set the Farm request explicitly. Windows large pages use the account's
  existing lock-pages privilege.
- **Host load.** The Ryzen host is a desktop that was not quiesced. Per-run
  `/proc/loadavg` over the 906 recorded runs ranged 0.62–8.22; the high end is
  the `tail` and Fiber `benchmark_mt` harnesses' own spinning threads. Cells
  whose spread is more than a few percent are called out in the text. The Intel
  laptop was on AC power with the Balanced power plan, without isolating the
  desktop. Windows load-average accounting is unavailable; ranges include all
  valid samples, not just the fastest ones.
- **Tail topology.** Windows uses native processor discovery. On Linux,
  `tail` and the Fiber `benchmark_mt` read
  `threadpool.topology` (`CacheAwarePool.topology()`), which needs
  `/sys/devices/system/cpu`. Only when `/sys/devices` is entirely absent, pass
  `--fake-topology`: the script synthesizes a tree from `/proc/cpuinfo` (cache
  sizes hard-coded for this Ryzen 5 5500; adjust for other hosts) at the
  hardcoded path, removes exactly what it created, and refuses on a real sysfs
  mount. It needs a writable non-sysfs `/sys`.

### What the units mean

| Unit | Benchmark | Meaning |
| --- | --- | --- |
| **Mpps** | `throughput`, `dual` | million payload `Call`s per second; one item is one published payload |
| **Mactor_cycles/s** | `actor_churn` | million complete actor lifecycles (create → dispatch → retire → reclaim) per second |
| **Mselected_callbacks/s** | `actor_churn subset*` | million selected subset callbacks per second |
| **Mactor/s** | `actor_ready` | million actor activations per second from a prequeued burst |
| **fibers/s** | `ant_fibers` DUB benchmarks | Fiber creations, scheduler resumptions, or full spawn-and-drain bursts as labeled |

comparable to each other and to `private`; a fanned-out cohort adds no units.

## Method

Build the harness once, then run the matrix into a scratch directory:

```sh
make -C tools/perf all
make -C tools/perf actor_churn_mimalloc       # real mimalloc archive must exist
python3 tools/perf/run_performance_md.py      # writes /tmp/antfarm-perf-report
python3 tools/perf/run_performance_md.py --sections tail,fibers --fake-topology
```

On Windows, prepare the Release allocator with
`tests/actors/run-mimalloc-windows.ps1 -Configuration Release`, then:

```powershell
./tools/perf/build-windows.ps1
python tools/perf/run_performance_md.py --out .build/performance-12700h --runs 5
```

The script writes `metadata.json`, one raw capture per run under `raw/<section>/`,
and `summary.json` with median/min/max per cell. It runs 5 times per cell with
`ANTFARM_HUGE_PAGES=0` unless a cell opts in. A run counts only when the process
exits 0 and its metric parses; a cell with fewer than 5 valid runs is failed and
the script exits nonzero. Re-running resumes a cell only when its stored argv
and env match. Raw output is archived, not committed.

The Ryzen regeneration ran 5 iterations per cell and re-ran the noisy
`farm_consumers`, `farm_best`, `private` and `fibers` sections with 9 iterations
because their 0- and 11-consumer cells are layout-sensitive. The tables say
which count Ryzen uses. Intel uses 5 runs per cell throughout; its raw captures
and machine-readable summary are in `.build/performance-12700h-2026-10-11/`.
The additional Intel 12/18/20-thread sweep and throughput grid search are
saved separately in `.build/performance-12700h-threads-2026-10-11/`.

The workload tables reproduce from the script's cells; the exact argv is each cell's
`cmd` in `summary.json`. Payload tables use the 16 MiB ring (`--ln 2097152
--k 8`); actor tables use the harness's 8 MiB ring, with the controller plus one
pinned worker per listed consumer.

Actor CPU lists use controller 0 and consumers 1 through N on both hosts;
0-consumer cells are unpinned. On Intel, LP pairs 0/1, 2/3, through 10/11 are
the six P cores and LPs 12 through 19 are E cores. Thus the 6-consumer actor
cell uses four P cores including three SMT pairs, not six separate cores.
The topology-aware tail benchmark instead uses P-core LPs 0, 2, 4, 6, 8, 10
for its consumers, LP 12 for its producer, and LP 13 for its mailbox.
For the private actor extension, 12/18/20 total threads mean 11/17/19
consumers plus the controller, pinned to LPs 0-11, 0-17, and 0-19 respectively.
The 12-thread cell uses all P-core SMT contexts; the larger cells add six
and eight E cores. Dual-role counts include every active worker; the coordinator
waits for them to finish. Dual-role and throughput workers are unpinned.

Compare a change against a committed ref with:

```sh
make perf-gate BASE=<sha> CANDIDATE=<sha>
make perf-gate BASE=<sha> PERF_GATE_ARGS=--control
```

Gate rules (full text in [tools/perf/README.md](../../tools/perf/README.md#performance-report)):

- Exit 0 pass, 1 regression, 2 inconclusive/error; inconclusive is never a pass.
  The regression boundary is **−3%** on the paired-median decision.
- Near the boundary, rerun with `PERF_GATE_ARGS=--boundary` for **≥20 process
  pairs** plus a byte-identical control (`PERF_GATE_ARGS=--control`, base built
  twice; hashes must match). Individual pairs may dip below −3% while the cell
  passes if the paired-median interval's lower bound is above −3%; harness bias
  is about ±1.5%.
- At 0 consumers code layout alone can move single-threaded cells; attribute a
  near-boundary swing with an inert-code control. That waiver is one-off.
- Run correctness first, then timing serially on a quiet host.

### Single-threaded table layouts vs MT tables

The comparison below describes the 1.8.x implementation and its measurements.
The 1.9 development branch removes MT payloads and full ring headers; its
current formats are documented in [SPEC](../../SPEC.md#2-data-layout). Historical
results here are not measurements of the 1.9 changes.

A table of only single-threaded payloads (`Tmt == 0`, every payload
`MaxCs == 1 && Done == 1`) stores each payload as a compact `[Call][Pbody]`
record (SPEC 2f), or, when the accepted prefix shares one `Call`, as the bare
`[Pbody]` with the `Call` stored once per table (SPEC 2g). A uniform table whose
bodies also share one nonzero length drops Tindex as well. A table containing a
multi-threaded payload keeps the full `Phead` layout. Geometry, ignoring table
overhead:

| Format | Ring words per entry | Entries per 4096-word small quota |
| --- | --- | ---: |
| Uniform `Call` and length, 1-word body | 1 (body) | ≈4096 |
| Uniform `Call` and length, 16-word body | 16 | ≈256 |
| Uniform `Call`, 1-word body | 2 (1 index + 1 body) | ≈2048 |
| Uniform `Call`, 16-word body | 17 | ≈241 |
| Compact ST, 1-word body | 3 (1 index + 1 `Call` + 1 body) | ≈1360 |
| Compact ST, 16-word body | 18 | ≈227 |
| MT full, 1-word body | 18 (1 index + 16 `Phead` + 1 body) | ≈227 |
| MT full, 16-word body | 33 | ≈124 |

Compact tables admit several times more entries per quota than the full layout,
which is why the per-object allocator geometry shifts in the private-remote
churn cell (see [Allocators](#allocators)); uniform tables admit up to three
times more again.

These benchmarks all build ST tables (the payload harnesses and actor layers
set `MaxCs = Done = 1`). The harnesses publish uniform tables wherever a table's
callbacks are shared (`throughput --mixed-calls` keeps the compact layout). The
MT path was exercised only by the correctness suite in 1.8.x (`antfarm_test`,
`tests/farm`).

The important case is the wide root table: a `tree` parent table at batch 1024
holds 16 roots, and the derived hint splits it into 8 two-entry claims across
the consumers (90.8 vs 17.6 on Ryzen, about 5.2×). A fixed class 2 (32-entry claims) or a
fixed class 0 (128-entry claims) makes the same 16-entry table a single claim on
one worker. Above the 64-entry small-table threshold the derived hint counts
claims per shard: a sharded table keeps 32-entry claims once they reach the
target, and a table just above the threshold uses shorter claims instead of one
claim per shard. That is why the batch-256 `tree` auto cell (class 3, 16-entry
claims) beats a fixed class 2 or 0 by about 25% on Ryzen.

On Ryzen, batch size for `private` at 6 consumers rises from 256 to 1024 (40.99 → 50.73,
about 1.24×) and falls back at 2048 (43.27); use the smallest batch that keeps
the park's reservation affordable.

**MT timing caveat:** workers execute while `burstSpawn` is still creating
Fibers. The harness's printed `run` rate divides all 100,000 Fibers by only
the residual drain time, overstating throughput when most work has already
finished. Intel cold readouts reached billions of fibers/s and are excluded.
The retained Ryzen legacy readouts have the same timing flaw; they are not
validated throughput and must not be compared with the full-burst rows.

The report driver now computes MT full-burst throughput as Fiber count divided
by the sum of the printed creation and drain durations. Intel's cold range is
wide (87k-250k fibers/s); the warm pool reaches 0.78M-1.42M. These are end-to-end
burst rates, not isolated scheduler rates. Comparable Ryzen full-burst timings
were not recorded here. Fixing the raw MT benchmark's timing labels remains
an open benchmark issue.

### What to compare

Ant Farm payloads and managed Fibers solve different problems:

- A payload is the fast path for short, non-suspending `nothrow @nogc` work.
- A managed Fiber pays for ordinary D control flow, suspension, waits, timers,
  joins, cancellation, completion, and stack reuse.
- A same-thread `Fiber.call` loop remains the right baseline for an application
  which only needs coroutines on one OS thread.

The useful system comparison is whether Fibers and payloads can share pinned,
topology-aware workers without blocking them, not whether an empty managed
Fiber can beat a direct `Fiber.call`.

### Assist-ring A/B

`benchmark_mt` binds one lane to each accepted LLC group through a
`FiberServicePlan`. Its second argument selects the domain and service layout:

- `private` (default): one domain per lane.
- `shared`: one domain over every lane, native service only, with no edges.
  This is the default service of a shared domain.
- `assist`: one domain plus an explicit `assistRing` over the accepted groups,
  the former automatic coverage ring with persistent remote subscriptions.

```text
ANTFARM_HUGE_PAGES=0 dub run -c benchmark_mt --build=release --compiler=ldc2 -- 100000 shared
ANTFARM_HUGE_PAGES=0 dub run -c benchmark_mt --build=release --compiler=ldc2 -- 100000 assist
```

Compare `shared` with `assist`; both use the same domain semantics. The ring
needs at least two accepted groups to create edges. On a two-LLC Ryzen 9
5900XT, an instrumented two-worker probe measured the ring 42% (one lane
loaded) and 73% (both loaded) slower than no edges. That is prior evidence,
not a gate. Alternate modes across repeated runs and report dispersion.

can penalize the first concurrent drain. Mixed Fiber/payload deployments must
measure the payload side separately: bare Farm table walks can still benefit
materially from huge pages even when `Fiber.call` and scheduler handoff are the
Fiber bottleneck.

### Scheduler rates

Representative warm and cold results for 200,000 tasks:

| Phase | Representative rate |
| --- | ---: |
| Cold create, single thread | ~147–153k Fibers/s |
| Warm create, single thread | ~3.2–3.6M Fibers/s |
| Warm run, single thread | ~3.4–4.2M resumptions/s |
| Warm run, multiple workers | ~6.9–8.1M resumptions/s |
| Warm create, multiple producers | ~2.0–2.3M Fibers/s |

Cold creation is dominated by DRuntime Fiber creation and stack mapping.
Changing Farm table size, `avgCost`, huge-page policy, or using a 4 KiB stack
did not materially change it. `FiberDomain.reserve` can avoid roots-array
growth for a known burst, but it does not pre-map Fiber stacks.

The common ready path uses one shared resume header and fixed one-word bodies.
It therefore selects Ant Farm's common-header/fixed-length write overload and
avoids per-body sizing. Empty-body Fiber throughput is nevertheless normally
limited by Fiber and scheduler handoff cost rather than Farm table sizing.

The `benchmark_vs_druntime` baseline reserves the DRuntime arrays, uses

### Worker topology sweep

The following run used 100,000 warm empty Fibers and control-thread-produced
payloads. The Fiber-oriented configuration was `flushBatch=256` with runs of
32 entries, and the alternate payload configuration was `flushBatch=32` with
runs of 8. These were recorded as `avgCost=0` and `avgCost=2` while `MAX_CHUNK`
was 32; the same runs are now `avgCost=2` and `avgCost=4`.

| Topology | Fiber rate | Payload rate |
| --- | ---: | ---: |
| 1 worker | 3.5M/s | 42M/s |
| 2 workers | 3.6M/s | 31M/s |
| 4 workers | 5.4M/s | 32M/s |
| 6 physical cores | 6.7M/s | 29M/s |
| 6 physical, 32 / 2 | 5.4M/s | **53M/s** |
| 12 SMT | **8.3M/s** | 32M/s |
| 12 SMT, 32 / 2 | 5.1M/s | 51M/s |

On this host, all 12 logical processors and large tables won for empty Fibers.
Six physical consumers and smaller chunks won for tiny payloads produced by a
control thread. Extra workers provided more `Fiber.call` sites but contended on
the serial payload ring.

These measurements motivate the two starting presets exposed by the Fiber
integration:

- `fiberThroughput`: all logical processors, `flushBatch=256`, `avgCost=2`
  (runs of 32);
- `payloadThroughput`: skip SMT siblings, `flushBatch=32`, `avgCost=4` (runs of
  8).

They are starting points, not portable policy. A mixed application should
benchmark both with its actual body and wake pattern.

### Embedding overhead

`benchmark_farm_embed` compares the same two-million one-shot payload workload

| --- | ---: | ---: |

### Tuning guidance

- Benchmark useful work. Empty bodies isolate scheduler overhead but do not
  predict a body that sleeps, waits, allocates, or performs substantial work.
- Keep bare payloads as the default for short serial compute. Use Fibers for
  work that actually needs suspension or structured D control flow.
- `flushBatch` and `avgCost` size a Farm table (`avgCost` is `0 .. 7`;
  consumers claim `128 >> avgCost` entries at a time). Production pumps use
  `consumeNext` and finish or yield the claimed table; use shorter tables when
  a scheduler visit must be shorter.
- Lower `flushBatch` when a responder must return to timer polling more often.
- Size Farm consumer and producer capacity from `plan.requirement(g)` (native
  workers plus the workers of any serving group), plus every control producer
  that can hold a registration.
- Call `FiberDomain.reserve(n)` before a known live burst to avoid roots-array
  reallocations.
- Treat huge pages as a payload-oriented opt-in and benchmark Fiber-only lanes
  both ways. On this host they did not improve recycled Fiber drain and slowed
  the first concurrent drain. Set `ANTFARM_HUGE_PAGES=0` for an explicit
  4K-backed profile and `=1` for a huge-page profile.
- Do not wrap scheduler entry or Farm consumption in `GC.disable`. First Fiber
  entry, stack registration, and user callbacks may allocate.
- Profile multi-producer cold admission before optimizing it. Cold stack
  mapping currently occurs while domain admission is serialized and may
  convoy concurrent spawners.

### Allocation profile

Bounded lifecycle reporting now retains its detached backlog count instead of
recounting the shrinking list on every call. This removes quadratic traversal
without changing DRuntime Fiber execution. The isolated 16,384-record,
batch-32 probe improved from 20.20 ms to 1.05 ms for handler delivery; see
[the scaling benchmark](../../tools/perf/README.md#scaling)
for host details, timing boundaries, and reproduction commands.

After warm-up, ready and completion MPSC publication, stack-snapshot flush,
fixed-width Farm publication, ready republishing, established waits, timer
expiry, lifecycle record reuse, and `Fiber.reset` task reuse do not allocate.

Allocation remains expected for cold Fiber/stack creation, roots or timer heap
growth, first insertion of a signal key, lifecycle setup, returned completion
and lifecycle arrays, shutdown snapshots, exception creation, and user code.
The recycle pool grows toward the concurrent live-Fiber high-water mark rather
than the historical spawn count.

### Reproducing the benchmarks

Run from `ant_fibers/` with an optimized LDC build:

```text
dub run -c benchmark --build=release --compiler=ldc2 -- 200000 256 0
dub run -c benchmark_mt --build=release --compiler=ldc2 -- 100000
dub run -c benchmark_vs_druntime --build=release --compiler=ldc2 -- 100000
dub run -c benchmark_farm_embed --build=release --compiler=ldc2 -- 2000000
dub run -c benchmark_actor_wave --build=release --compiler=ldc2 -- 32768 200 6 20 0 8
dub run -c benchmark_actor_wave --build=release --compiler=ldc2 -- 32768 200 0 20 0 8 --smt --sweep
```

- `benchmark` characterizes cold/warm creation and single-thread drain.
- `benchmark_mt` measures concurrent Fiber drain, one lane per accepted LLC
  group; see the assist-ring A/B above.
- `benchmark_vs_druntime` compares DRuntime, managed Fibers, bare payloads, and
  worker topologies. Its single lane binds to one LLC group, so its worker
  sets come from the group of the first eligible CPU (`benchmark_farm_embed`
  and `benchmark_actor_wave` do the same). On multi-LLC hosts these runs are
  capped to one LLC's CPUs and are not comparable to earlier all-CPU runs
  there.
- `benchmark_farm_embed` isolates direct Farm, threadpool, and Fiber-pump
  embedding cost on the same payload.
- `benchmark_actor_wave` compares one Fiber producing two actor waves against
  two Fibers producing one independent wave each. Both cases commit one shared
  top-down generation only after both sets finish. Each actor contains one
  cache-padded private word and two cache-padded public words; its operation is
  only an identity projection through those lines. Arguments are actors per
  set, measured generations, maximum selected workers (`0` means all), warm-up
  generations, `avgCost` (default 2, runs of 32 entries), and Farm ring size in MiB
  (default 8, power of two).
  `--smt` includes sibling logical processors after selecting one worker per
  physical core. `--sweep` recreates the Farm and worker pool for every prefix
  from one worker through that selected set, then prints a compact Mactor/s
  summary. The positional worker maximum caps the sweep; zero uses every
  available physical worker of the first eligible LLC group, or every logical
  processor of that group with `--smt`.

#### Actor-wave optimization checkpoint

The first guided pass used a Ryzen 5 5500, six non-SMT workers, ordinary 4 KiB
pages, LDC release mode, 32,768 actors per set, 200 measured generations, and
the median of three runs. Costs are nanoseconds per actor dispatch:

| implementation | one Fiber | two Fibers |
|---|---:|---:|
| initial wave path | 286.50 | 211.63 |
| omit redundant wave `scheduled -> running` RMW | 268.98 | 193.78 |
| reserve only the exact Farm-accepted prefix | 40.99 | 36.94 |
| remove redundant per-member submission pins | 39.51 | 36.38 |

The accepted changes reduce median cost by 7.25x and 5.82x respectively.
Exact-prefix reservation is the decisive change: the old path reserved the
entire remaining slice and cancelled its unwritten tail for every physical
table, creating a shrinking-tail quadratic scan. Packing wave generation and
status into one atomic word and removing a duplicate admission load were also
measured. Neither improvement survived repeated sampling, so both were
reverted rather than paying semantic or maintenance costs without evidence.

Replacing completion and two-producer rendezvous polling with counted Fiber
generation triggers was measured separately with the 8 MiB ring. At 500
generations after 20 warm-ups, median cost was 36.34 ns/actor for one Fiber and
29.27 ns/actor for two. Retaining scheduler-created wait keys made the final
medians 36.25 and 29.22 ns/actor respectively, within ordinary run variance,
while removing repeated wait-bucket allocation. Only Farm publication
backpressure now uses cooperative
yields; completion parks on the scheduler wait path. Typical measured yields
fell from hundreds per generation to roughly 4--12, depending on run timing.
The completion callback itself remains `nothrow @nogc`: it advances a counter
and enqueues one preallocated deferred node, which a managed worker converts
to a normal cancellable FiberEvent wake after payload dispatch.

#### Actor-wave worker scaling

A full worker-prefix sweep on 2026-09-02 used the same Ryzen 5 5500, an LDC
release build, ordinary 4 KiB pages, the 8 MiB Farm ring, 32,768 actors per
set, 200 measured generations after 20 warm-ups, and runs of 32 entries
(`avgCost=0` at the time, now `avgCost=2`). The first
six workers select one logical processor from each physical core; workers
7--12 add those cores' SMT siblings. This was one ordered characterization
sweep rather than a median of independent runs:

| Workers | SMT siblings | One Fiber Mactor/s | Two Fibers Mactor/s | Two / one |
|---:|---:|---:|---:|---:|
| 1 | 0 | 16.49 | 16.22 | 0.984x |
| 2 | 0 | **24.56** | 23.73 | 0.966x |
| 3 | 0 | 24.44 | 28.50 | 1.166x |
| 4 | 0 | 24.55 | **30.96** | 1.261x |
| 5 | 0 | 23.84 | 30.84 | 1.294x |
| 6 | 0 | 23.30 | 30.87 | 1.325x |
| 7 | 1 | 22.34 | 28.04 | 1.255x |
| 8 | 2 | 22.08 | 27.35 | 1.238x |
| 9 | 3 | 21.27 | 27.18 | 1.278x |
| 10 | 4 | 20.88 | 26.50 | 1.269x |
| 11 | 5 | 20.54 | 26.68 | 1.299x |
| 12 | 6 | 17.37 | 23.37 | 1.345x |

One orchestration Fiber gets nearly all of its scaling from the second
physical worker: throughput rises 49% from one to two workers, remains around
24.5 Mactor/s through four, and then declines. Two independent producer
Fibers are slightly slower at one and two workers, where their rendezvous and
publication overhead have no spare execution capacity. They overtake the
single producer at three workers, peak at four, and hold approximately 30.8
Mactor/s through all six physical cores. At six workers the two-Fiber workflow
is 1.33x as fast as one Fiber, but neither workflow scales linearly with core
count.

Adding SMT siblings is uniformly detrimental to absolute throughput in this
sweep. From six physical workers to all twelve logical workers, the one-Fiber
case falls 25% and the two-Fiber case falls 24%. The apparent two/one ratio at
twelve therefore reflects the single-producer path degrading more, not an SMT
throughput win. Full SMT also raised publication-backpressure churn sharply in
this run, to 116 cooperative yields per generation for one Fiber and 151 for
two, compared with 8 and 10 respectively at six physical workers.

This benchmark performs only the identity projection through each actor's
private and double-buffered public cache lines. Its useful conclusion is that
the wave transport has enough independent work to benefit from a few physical
workers and from two producers, while its empty behavior becomes limited by
Farm publication, cache traffic, and orchestration before all physical cores
are saturated. Actor behaviors with more computation may move that knee and
should repeat the sweep rather than adopting four workers as policy.

#### Actor-wave Farm ring size

This host has one 16 MiB L3. After installing counted Fiber triggers, a
follow-up comparison used the same six physical workers, 32,768 actors per
set, 500 measured generations, and 20 warm-up generations. Each value is the
median of three runs with ordinary 4 KiB pages:

| Farm ring | one Fiber | two Fibers |
|---|---:|---:|
| 16 MiB | 39.75 ns/actor | 36.54 ns/actor |
| 8 MiB | 36.82 ns/actor | 29.90 ns/actor |

The 8 MiB ring improves the one-Fiber case by 7.4% and the two-independent-
Fiber case by 18.2%, despite incurring a few publication-backpressure yields
where 16 MiB incurred almost none. Cache footprint outweighs extra producer
slack for this workload, so 8 MiB is the characterization-host default. This
is not evidence for changing the general Farm default: the actor state alone
is 12 MiB, and the result may depend on this LLC, concurrent producer pattern,
table geometry, and state footprint.

Record compiler version, build mode, CPU topology, huge-page setting, task
count, warm/cold state, and batch parameters with any published result.

## Tuning guide

The detailed tuning observations below describe the Ryzen 5500 experiments.
Use the Intel column as a host-specific screen, not as a new default-setting
decision or a paired regression gate.

- **Batch size vs `avgCost`.** Batch size is the dominant knob; larger batches
  amortize table overhead up to about 1024, after which the curve flattens. The
  16-entry default claim is a latency-conserving choice. On uniform tables
  (SPEC 2g) one-way publishing barely depends on the class. Classes 0–2
  (128/64/32) buy a few percent for dual-role and compact (several-callback)
  tables and are the opt-in for throughput-bound publishing. Do not pay a
  longer claim for work that parks. See
  [Defaults on uniform tables](#defaults-on-uniform-tables).
- **Explicit work-cost hints.** Prefer `rootCostHintAuto` for private root
  tables. A fixed class is only for deliberately serializing or sharding: the
  batch-1024 tree case is about 5.2× slower with a fixed 32- or 128-entry claim
  than with the derived 2-entry claim. A cheap-parent table just above the
  small-table threshold keeps its derived split.
- **Child wave hints.** Child waves default to 32-entry claims and take a
  per-wave override. The override was neutral on the committed `tree` and
  `tree-slab` harness at 6 consumers; measure your own shape before opting in.
- **Public flush and wave.** The public defaults claim 8 entries; the pre-RC
  chunk 32 is within a few percent except `actor_ready`, where chunk 32 is about
  6% faster.
- **Huge pages.** On the headline configuration plus `--huge`
  (`ANTFARM_HUGE_PAGES=1`), huge pages are neutral (1,704 vs 1,692 Mpps) and
  neutral for actor work (`actor` 17.45 vs 17.45; `tree` 73.84 vs 74.41). Treat
  them as a payload opt-in; the Fiber package document documents a
  first-concurrent-drain penalty.
- **Quota tiers.** A 4096-word small quota admits about 4000 one-word entries
  in a uniform table (one callback, one body length), about 2000 with one
  callback and mixed lengths, about 1360 compact entries, and 227–256 at
  16-word bodies. Larger batches are split into accepted prefixes, so size
  `quotaSmall`/`quotaBulk` for the batch you publish.
- **Allocator choice; slab.** mimalloc is decisively faster than the C runtime
  for per-object actor state, and the cohort slab is faster still when a cohort
  retires together. Emitter-side reclamation is the default and avoids remote
  frees; consumer-side reclamation costs roughly two thirds of throughput at 6
  consumers.
- **Pinning and SMT.** The pinned `actor` curve peaks at 4 consumers (22.79
  Mactor_cycles/s), drops to 17.47 at 6, and an unpinned 6-consumer cell reaches
  21.68. The harness pins the controller to CPU 0 and consumer *i* to CPU *i*,
  so the 6-consumer cell puts consumer 6 on CPU 6, the controller's SMT sibling
  — the same physical core. That fits the 4 → 6 drop and the pinned-vs-unpinned
  gap, and means the flat 6 → 11 comparison already starts with one sibling.
  `tree` is unaffected (73.95 vs 73.47).
- **Known pathologies.** Tiny root tables concentrate all claims on shard 0, so
  a 1% subset at 6 consumers is much slower than the 10% or whole cases. Wide
  root tables with a fixed coarse claim collapse onto one worker (batch-1024
  `tree`). Attribute 0-consumer layout swings with an inert-code control.

This is the retained Ryzen 5500 sweep, not a fresh two-host defaults sweep.

The host is a desktop that was not quiesced, so ratios within about ±2% are
noise. 0-consumer cells spread by ±5–8% and are layout-sensitive. The RC changed
only the public flush/wave default (to the runtime's 8-entry claim) and added
the child wave override; the other rows are the uniform-layout sweep and are not
re-measured here.

### Open tuning opportunities (measured opportunity, not default)

Nothing here is changed; each would need its own gate.

- **Child/subset admission geometry.** The subset 1%/6 cell shows tiny tables
  centralize; a larger claim cannot fix a sub-threshold table, which shard 0
  claims wholesale.
- **Public flush/wave claims.** A derived class like the root hint's could
  take the wide-flush gains without making a small flush one claim. The RC
  default (chunk 8) is already within a few percent of chunk 32.
